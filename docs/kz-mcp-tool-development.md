# KZ MCP Tool Development

This document records the KZ MCP tool work in small, testable stages. The goal is to keep the toolset focused on mapper control: shape, intent, metadata, and metrics. It should not drift into a pile of fixed bhop prefabs.

## Principles

- TrenchBroom remains the source of truth. MCP tools do not write `.map` files directly.
- KZ tools should expose local mapper intent, not whole-map generation.
- Prefer shape vocabulary and batch polygon creation over repeated box spam.
- Prefer geometry metrics and warnings over claims that a route is playable in CS1.6.
- Keep writes transactional and undoable.
- Keep metadata session-local until there is a clear persistence design.

## Stage 1 Scope

Stage 1 implements the lowest-risk tools from `KZ_MCP_TOOL_REQUIREMENTS.md`:

- `shape_library_list`
- `brush_create_polygon_batch`
- `brush_metadata_set`
- `brush_metadata_get`
- `selection_by_metadata`
- `kz_distance_analyze_chain`

Deferred from Stage 1:

- `brush_chamfer_or_cut`: cutting existing brushes needs stronger geometry rollback tests.
- `route_platform_chain_create`: this is useful, but it risks becoming a prefab generator before shape and metadata tools settle.
- `platform_affordance_analyze`: this needs direction, landing window, and false-affordance rules that are easier to build after metadata is used in real routes.
- `route_reflow`: destructive route edits should wait until selection and metadata workflows are proven.

## Implemented Tools

### `shape_library_list`

Read-only. Returns the first KZ footprint vocabulary:

- `box`
- `diamond`
- `trapezoid`
- `chamfered_rect`
- `half_hex`
- `arrowhead`
- `slanted_plank`

The result names the intended use of each shape and whether it can be generated by `brush_create_polygon_batch`.

### `brush_create_polygon_batch`

Edit mode only. Input:

```json
{
  "brushes": [
    {
      "points2d": [[0, 32], [32, 0], [64, 32], [32, 64]],
      "minZ": 0,
      "maxZ": 16,
      "material": "optional",
      "metadata": {
        "routeId": "intro",
        "movementType": "bhop",
        "outgoingDirection": [1, 0, 0]
      }
    }
  ],
  "grid": 16,
  "select": true,
  "transactionName": "MCP: KZ polygon platforms",
  "detail": "summary"
}
```

The tool converts each item to a `blockout_create_batch` `prism` operation, so it reuses the existing batch compiler, validation, operation history, and transaction path. All polygons must stay convex after grid snapping. If any polygon fails, no brush is committed.

Default output is compact:

- `operationId`
- `transactionName`
- `brushCount`
- `changedObjectCount`
- `bounds`
- `validation`
- `resourceUri`

Use `detail=ids` when a caller needs object ids for follow-up metadata or analysis.

### `brush_metadata_set` / `brush_metadata_get`

Metadata is stored in the MCP bridge session. It is not written into the map file.

Supported metadata keys:

- `routeId`
- `intent`
- `difficulty`
- `movementType`
- `takeoffEdge`
- `landingWindow`
- `incomingDirection`
- `outgoingDirection`

If the map is reloaded or an object id stops resolving to a live brush, reads report the record as stale.

### `selection_by_metadata`

Read-only. Finds live brushes by session metadata and optionally selects them. It supports exact matching on:

- `routeId`
- `intent`
- `difficulty`
- `movementType`

This lets an Agent select a route segment without manually carrying long object-id lists through the conversation.

### `kz_distance_analyze_chain`

Read-only. Accepts ordered `objectIds` or a `routeId`. It computes mapper geometry metrics for each adjacent pair:

- `edgeGap`
- `effectiveDistanceIdeal`
- `effectiveDistanceBadLanding`
- `heightDelta`
- `lateralOffset`
- `landingWindowArea`

The tool uses `outgoingDirection` or `incomingDirection` metadata when present. Without direction metadata it uses platform centers and emits a warning. The result is a mapper heuristic, not an in-game pass/fail guarantee.

## Recommended Agent Flow

1. Call `shape_library_list` to choose a footprint.
2. Call `brush_create_polygon_batch(detail=ids)` to create the platforms in one transaction.
3. Use metadata in the batch call, or call `brush_metadata_set` afterward.
4. Use `selection_by_metadata(routeId=..., select=true)` for route edits.
5. Call `kz_distance_analyze_chain` with ordered ids before judging difficulty.
6. Use `history_undo_mcp` for rollback if the batch does not match the intended route.

## Validation Notes

Stage 1 validates:

- required schema fields for polygon batch
- convex polygon creation
- rejected non-convex polygons
- one transaction for a multi-platform batch
- undo removes the whole batch
- metadata set/get/select
- basic KZ distance metrics for a two-platform chain

Stage 1 deliberately does not validate actual CS1.6 movement viability. Server settings, plugin rules, player speed, landing state, and in-game physics still need manual testing.

## Next Risks

- Session metadata is useful but temporary. A future persistent metadata design needs an explicit map-safe storage strategy.
- Direction metadata is optional, so distance analysis can be low-confidence. Route tools should prefer ordered ids and direction vectors.
- Polygon batch only creates vertical convex prisms. Concave footprints must be split into multiple convex brushes by the caller or a future compiler.
- Chamfer/cut tools need stronger tests around invalid brush rollback before they are safe for Agent use.
